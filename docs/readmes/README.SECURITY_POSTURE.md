# RedAmon Security Posture

> **What this document is.** RedAmon is offensive software, so we hold it to the standard it tests others by. This is the **defense-in-depth control catalog**: every security layer implemented in the product, grounded in repository evidence (source, `docker-compose.yml`, nginx templates, deploy scripts). It is the companion to the **[Threat Model](README.TM.SYSTEM_OVERVIEW.md)**, which describes the assets, trust boundaries, entry points, and network surface the analysis is built on. Read the threat model for "what exists and what it is worth"; read this for "how each of those things is defended."
>
> **Methodology.** The platform was assessed with a systematic, adversarial threat-modeling pass (a STRIDE-style analysis across every trust boundary: spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege). Findings were remediated in sequenced, independently verified waves, each fix carrying a test and, where applicable, a before-and-after exploit reproduction. This document catalogs the resulting controls; the per-release history lives in the **[Changelog](../../CHANGELOG.md)** security entries.

## 1. Security principles

Five principles drive every control below.

- **Secure by design.** Security is a property of the architecture (privilege separation, network segmentation, a least-trusted target-facing worker that holds no secrets), not a bolt-on.
- **Fail closed.** In the hardened posture every authentication and authorization control rejects on absence or error rather than serving. Where a control fails open, it does so only in a local dev stack with a one-time warning, and `redamon.sh` auto-generates the secret that flips it closed. The internet-facing deploy additionally runs a secrets gate that refuses to boot with any weak or unset secret.
- **Least privilege.** Each component holds only the credentials it needs. The worker holds none; scanners hold a scoped key, not the master key; the graph worker reads through a tenant-filtered proxy with no database credentials of its own.
- **Defense in depth.** No single control is load-bearing. The agent WebSockets, for example, sit behind an app-layer signed ticket, a server-side same-origin check, an nginx session-cookie gate, an operator IP allowlist, and a host firewall.
- **Evidence over claims.** Every control here maps to a file in the repository, and every security fix shipped with a test. Accepted residual risks are documented in the open (see [Section 20](#20-documented-residual-risks)).

## 2. Two deployment postures

RedAmon supports two postures with different trust models. The controls that apply depend on which one you run.

| | **Local (default)** | **Public-internet (hardened)** |
|---|---|---|
| Provisioned by | `redamon.sh` / `docker compose` | `tooling/deploy/single-host/deploy.sh` |
| Attacker model | No anonymous internet attacker; operator LAN only | **Anonymous internet attacker is a first-class actor** |
| `webapp:3000`, `agent:8090`, `revshell:4444` | Published on `0.0.0.0` (LAN-reachable) | Re-bound to `127.0.0.1`; only nginx `443` faces the internet |
| TLS | None | TLS 1.2/1.3, HSTS, single public origin |
| Edge controls | None | nginx gate, rate limiting, header stripping, WS session gate |
| Host controls | None | ufw, fail2ban, SSH hardening, unattended upgrades |
| Secrets | Auto-generated; weak values warn only, except the plugin preflight's (Section 14), which refuses to start | Secrets gate **refuses to boot** on any weak/unset secret |

The base platform is designed local-only and deliberately does not ship the internet-facing layer; the `tooling/deploy/single-host/` tool adds it. A plaintext `http-*` lab mode exists but is gated behind an explicit `ALLOW_INSECURE=1` opt-in and drops TLS/HSTS; it is for throwaway labs only. Sections 3-5 below are the hardened-posture layers; Sections 6-17 apply to both postures (they are in the application and infrastructure themselves).

## 3. Network exposure and the single public origin

**Goal: from the internet, exactly one thing is reachable, the webapp login over HTTPS.** Everything else is bound to host loopback and reached only internally.

Host-published port bindings (`docker-compose.yml`, and the `tooling/deploy/single-host/compose/docker-compose.prod.yml` overlay that re-binds the last LAN-facing ports to loopback in the hardened posture):

| Port | Service | Local bind | Hardened bind |
|---|---|---|---|
| 3000 | webapp | `0.0.0.0` (LAN) | `127.0.0.1` (via nginx 443 only) |
| 8090 | agent | `0.0.0.0` (LAN) | `127.0.0.1` (nginx proxies only `/ws/*`) |
| 4444 | reverse-shell catcher | `0.0.0.0` (LAN, direct shells) | `127.0.0.1` (ufw-opened per engagement) |
| 8010 | recon-orchestrator | `127.0.0.1` | `127.0.0.1` |
| 5432 | PostgreSQL | `127.0.0.1` | `127.0.0.1` |
| 7474 / 7687 | Neo4j HTTP / Bolt | `127.0.0.1` | `127.0.0.1` |
| 8000/8002/8003/8004/8005 | Kali MCP servers | `127.0.0.1` | `127.0.0.1` |
| 8013 / 8014 | MSF / Hydra progress | `127.0.0.1` | `127.0.0.1` |
| 8015 | tunnel manager | `127.0.0.1` | `127.0.0.1` |
| 8016 | terminal PTY | `127.0.0.1` | `127.0.0.1` |
| 4040 | ngrok API | `127.0.0.1` | `127.0.0.1` |
| 7071 / 7072 | plugin-gateway proxy | not published | not published |
| 7080 | plugin runner supervisor | not published | not published |
| 80 / 443 | nginx (host service) | not present | `0.0.0.0` (the public origin) |

Containers still bind `0.0.0.0` **inside their own network namespace** so cross-container bridge traffic works; only the *host publish* is loopback-scoped. The datastores and the MCP tool surface were moved to loopback and the reverse-shell catcher is intentionally routable in the local posture (a compromised target must be able to connect back); in the hardened posture it is closed at the firewall and opened only per engagement (see [Section 13](#13-agent-safety-controls)).

**Post-deploy verification.** `deploy.sh` asserts the network model after every deploy (`tooling/deploy/single-host/deploy.sh`): it reads `ss -tlnH` and fails if `3000`/`8090` are missing or bound off-loopback, and fails if any of `5432`/`7474`/`7687`/`8010` is bound off-loopback. It then confirms container health, that an admin user exists, and that `https://<host>/api/health` returns 200.

**Cloud firewall.** Because Docker's iptables chains can bypass a host firewall, the provider firewall (AWS Security Group / GCP firewall / Azure NSG) is the reliable outer boundary. The deploy opens only **443** (app), **80** (ACME challenge + HTTPS redirect), and **22** (SSH, operator IP only).

## 4. Edge hardening (nginx)

nginx runs as a **host service** (not a container), sits **only at the edge** on 80/443, and reverse-proxies to two loopback backends: the webapp (`127.0.0.1:3000` for `/` and `/api/*`) and the agent (`127.0.0.1:8090` for only the four `/ws/*` paths). It is not a middlebox between containers. Templates: `tooling/deploy/single-host/nginx/redamon.conf.tmpl` and the `snippets/`.

**Single-origin proxy model.** The only agent routes proxied are `~ ^/ws/(agent|kali-terminal|cypherfix-triage|cypherfix-codefix)$`. The agent's entire REST surface (`/graph/exec`, `/emergency-stop-all`, `/mcp/*`, `/llm/*`, `/workspace/*`, `/sessions/*`) has no nginx route and stays loopback-only. Port 80 serves only the ACME challenge and a `301` redirect to the canonical HTTPS host (not `$host` in domain mode, to prevent open-redirect / cache poisoning).

**TLS.** TLS 1.2 and 1.3 only; ECDHE-only cipher suites (AES-GCM + CHACHA20-POLY1305); `ssl_session_tickets off` (forward secrecy); OCSP stapling on; curve list `X25519:prime256v1:secp384r1`; `ssl_prefer_server_ciphers off`.

**HSTS.** `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` (2 years), emitted in HTTPS modes (toggle `HSTS_ENABLE`, default on).

**Security headers** (nginx is authoritative because the webapp sets none of its own, `snippets/security-headers.conf`):

- `Content-Security-Policy` with `default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, and **no `unsafe-eval`**. It does carry `'unsafe-inline'` on `script-src`/`style-src` (a Next.js/WebGL constraint), so the CSP is a hardening layer, not an XSS silver bullet. Shipped as `Content-Security-Policy-Report-Only` by default and promoted to enforcing via `CSP_ENFORCE=true` once the graph and terminal are confirmed rendering.
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`.
- `Permissions-Policy` denying accelerometer, autoplay, camera, display-capture, geolocation, gyroscope, magnetometer, microphone, payment, usb, and interest-cohort.
- `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`.
- Dotfiles and sensitive extensions (`.env`, `.pem`, `.key`, `.crt`, `.sql`, `.bak`, `.git`, ...) return `404`.
- The `/api/auth/login` location adds `Cache-Control: no-store` and re-emits the security headers (an nginx `add_header` in a location drops server-level headers), so the auth-cookie response is never cached.

**Inbound trust-header stripping** (`snippets/proxy-common.conf`). On every proxied request nginx clears `X-Internal-Key`, `X-Scanner-Key`, `X-User-Id`, and `X-User-Role` (the webapp trusts these from internal callers), pins `X-Forwarded-For`/`X-Real-IP` to the real peer rather than appending the client-supplied chain, and hides `X-Powered-By`. A client therefore cannot spoof identity or replay an internal service key from the edge.

**Plugin-internal routes are closed at the edge.** `location ^~ /api/plugin-gateway/`, `^~ /api/plugin-runner/` and `^~ /api/internal/plugins/` all `return 404`, in both the `https` and the `http-*` templates. They serve only the internal plugin-gateway proxy and the orchestrator, and the first two skip the session cookie (they take a call token or the runner key), so they are never offered to the internet even though a valid credential would still be required.

**WebSocket session gate.** With `WS_REQUIRE_SESSION=true` (default), nginx runs an `auth_request` against an internal `/_redamon_session` validator (which proxies to the webapp's `/api/auth/me` with body off and the trust headers stripped) before allowing any `/ws/*` upgrade. Reaching an agent socket therefore requires a logged-in session, on top of the app-layer ticket.

**Operator gate.** The whole `443` server sits behind `GATE_MODE`: `ip_allowlist` (nginx `allow`/`deny` from `OPERATOR_ALLOW_CIDRS`), `basic_auth` (htpasswd via `openssl passwd -apr1`), or `none`. Leaving `OPERATOR_ALLOW_CIDRS` empty makes ufw open 443 (and SSH) to the world with a loud warning, so set it.

**Rate limiting and anti-DoS.** `limit_req` of **5 requests/min** (burst 3) on `/api/auth/login` and **30 requests/sec** (burst 60) on `/api/`, both returning `429`; `limit_conn 20` per IP; slowloris timeouts (`client_body_timeout`/`client_header_timeout`/`send_timeout` 15s, `keepalive_timeout` 20s); `large_client_header_buffers 8 32k`; `client_max_body_size 60m`; a method filter returning `405` for anything outside `GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS`; `server_tokens off`; `autoindex off`.

## 5. Host hardening

Applied idempotently by `tooling/deploy/single-host/deploy.sh` and `modules/`.

**Firewall (ufw, `modules/firewall.sh`).** `default deny incoming`, `default allow outgoing`. SSH scoped to `SSH_ALLOW_CIDRS` (falling back to `OPERATOR_ALLOW_CIDRS`); HTTPS/443 scoped to `OPERATOR_ALLOW_CIDRS`; HTTP/80 left world-open (Let's Encrypt validates from arbitrary IPs). If a CIDR list is empty the corresponding port opens to the world with an explicit warning. Port 4444 stays closed; it is opened per engagement only, scoped to RoE target CIDRs.

**SSH hardening (`modules/ssh_hardening.sh`).** `PermitRootLogin no` and pubkey auth always. Password login is disabled **only** when the deploy itself used key auth; deploying over a password leaves password login enabled so the operator cannot be locked out (a documented safety valve). Changes are validated with `sshd -t` before any restart; a bad config aborts without restarting. Also tightens `~/.ssh` and `/etc/shadow` permissions.

**fail2ban (`modules/fail2ban.sh`).** Jails for `sshd` (systemd backend, maxretry 3, bantime 2h), `nginx-http-auth`, `nginx-badbots` (bantime 24h), and `nginx-limit-req`.

**Unattended security upgrades (`modules/unattended_upgrades.sh`).** Automatic daily package-list update and unattended security-upgrade installation.

**Host bootstrap (`modules/host_bootstrap.sh`).** Detect-and-install matrix that is idempotent and hard-fails on a half-provisioned host: base packages, Docker Engine (>= 28.0.0, which the plugin networks need) + Compose v2 (>= 2.24) from Docker's official GPG-verified repo (purging any conflicting `docker.io`/v1 packages first; installed or upgraded when either is too old, and a hard failure when either still is afterwards), nginx, certbot (only when Let's Encrypt is used), ufw, fail2ban, unattended-upgrades, an 8 GB swapfile (mode 600) on hosts under 16 GB RAM, optional Docker DNS, and raised inotify limits. The whole matrix runs in `init` and `harden`; `update` runs its Docker step before the pull, so the Engine 28 floor is enforced on all three.

**TLS provisioning (`modules/tls.sh`).** Let's Encrypt (webroot ACME, auto-renew wired through certbot's timer with an nginx-reload deploy hook), operator-provided certificates (installed at `/etc/ssl/redamon/`, key mode 600, md5-idempotent, decrypting an encrypted key with `SSL_KEY_PASSWORD`), or self-signed for bare-IP labs. Private keys are always mode 600.

## 6. Authentication and session security

Application layer, both postures. Evidence: `webapp/src/lib/auth.ts`, `middleware.ts`, `lib/loginThrottle.ts`, `lib/cookieSecurity.ts`, `app/api/auth/*`.

**Login and JWT.** Passwords are hashed with **bcrypt at cost factor 12** (`bcryptjs`), compared in bcrypt's own constant-time routine. On success the webapp issues an **HS256 JWT** (`jose`) with `{ sub: userId, role }`, a **7-day** expiry, in the httpOnly cookie `redamon-auth`. The signing secret is `AUTH_SECRET`, and the code **throws if it is unset or the literal `changeme`**. Verification rejects any token missing `sub` or `role`.

**Cookie flags.** `httpOnly`, `SameSite=Lax`, `Path=/`, `maxAge` 7 days, and `Secure` set from the request (`x-forwarded-proto === 'https'` in production, `lib/cookieSecurity.ts`) rather than hardcoded, so the Secure flag is correct behind the deploy's TLS terminator without breaking a plain-HTTP local stack.

**Route protection (`middleware.ts`).** Every route requires a valid `redamon-auth` JWT except a tight public allowlist: `/login`, `/api/auth/login`, `/api/auth/logout`, `/api/health`, `/api/version/check`, `/api/global/tunnel-config/sync`, plus static assets. On success the middleware overwrites `x-user-id`/`x-user-role` from the verified token (a client cannot inject them). Missing token yields 401 (API) or a redirect (page); an invalid token additionally deletes the cookie. Two prefixes skip the cookie but not authentication: `/api/plugin-gateway/v1/` (a plugin call token) and `/api/plugin-runner/v1/` (`PLUGIN_RUNNER_KEY`). Each ends in `/`, so a look-alike such as `/api/plugin-gatewayx` stays behind the cookie.

**Login lockout (`lib/loginThrottle.ts`).** In-memory throttle keyed by **both** lowercased email and source IP: **5 attempts** (`LOGIN_MAX_ATTEMPTS`) then a **900-second** lockout (`LOGIN_LOCKOUT_SECONDS`) over a rolling 15-minute window, returning **429 with `Retry-After`**. The store is bounded at 10,000 entries with oldest-first eviction so a distinct-IP flood cannot exhaust memory. The per-IP key is applied only when the client IP is trusted (`TRUST_PROXY`), so a spoofed `X-Forwarded-For` cannot cause lockout evasion or collateral lockout of a real user. In the hardened posture the nginx `limit_req` on the login route is a second, network-level brake.

**CSRF stance.** State-changing routes are protected by `SameSite=Lax` cookies plus the nginx inbound trust-header stripping; there is no separate anti-CSRF token, so Lax is the load-bearing control here (noted as a residual in [Section 20](#20-documented-residual-risks)).

Failed and successful logins, logout, and lockouts are all audited (see [Section 16](#16-audit-and-non-repudiation)); audit records never contain the password or hash.

## 7. Authorization and multi-tenancy (BOLA)

RedAmon is multi-tenant: every user owns their projects, graph, conversations, scans, remediations, reports, presets, workspace files, and settings. Evidence: `webapp/src/lib/access.ts`, `lib/session.ts`, `graph_db/tenant_filter.py`.

**Per-user object ownership.** A single trust core scopes every request to an **effective user**. A standard user is always their own id (any client-supplied `userId`/path id is ignored for ownership). Reusable guards (`guardProject`, `requireProjectAccess`, `requireConversationAccess`, `requireProjectScopedResource`, `requireUserAccess`, `ownerScope`) enforce ownership on every data route. Enforcement is **on by default** (`ACCESS_ENFORCE`, fail-closed) with a log-only phase available for rollout. Cross-user access returns **404, not 403** (anti-enumeration: an attacker cannot even confirm a resource exists); secret-exposure routes use an immediate 403 instead.

**Admin impersonation is server-enforced.** An admin acts as their own id unless actively simulating user X through a signed, httpOnly `redamon-act-as` cookie (`{ sub: adminId, act: targetId }`, 12-hour expiry) minted only by the admin-only `POST /api/auth/act-as`. `getEffectiveUser` honors the act-as cookie only when it was minted by that same admin, and act-as can only narrow an admin to one user, never elevate a standard user. The agent WebSocket ticket binds the **effective** user, so a simulated session acts as the target, not the admin. Logout clears both cookies. (On a small set of user-secret GET routes an admin can still read masked values without act-as, a legacy convenience flagged in code for subsumption; it is a read, never a write.)

**Graph tenant isolation (`graph_db/tenant_filter.py`).** Every Cypher query is rewritten to inject `user_id` and `project_id` predicates onto every labeled node pattern, as bound parameters, before it reaches Neo4j (which is Community edition and has no row-level RBAC). The read-only worker proxy (`/graph/exec`) additionally refuses an unlabeled `MATCH (n)` so the tenant filter can always apply. A single filter module is shared by the agent and the worker-facing proxy.

**Mass-assignment defense.** Project create/update whitelists writable fields against the Prisma model metadata and strips server-managed fields; user-secret update routes re-mask secrets and reject non-settable fields before the body reaches the ORM (`webapp/src/app/api/projects/route.ts`, `users/[id]/*`).

**Rules of Engagement documents are the owner's.** The download of a project's RoE document and of its superseded versions (`/api/projects/[id]/roe/download`, `.../roe/revisions/[revId]/download`) requires the effective user and project access (404 otherwise), serves the stored name per RFC 6266 and the media type only from an allowlist, with `nosniff`, and is audited (`project.roe.download`). Replacing or removing a RoE (`POST`/`DELETE /api/projects/[id]/roe`) and parsing one (`/api/roe/parse`) also require the same origin, as the plugin routes do.

**A user's agent skills are written only by that user's own browser session.** Batch upload (`POST /api/users/[id]/attack-skills/batch`), the batch name check (`POST .../name-check`) and Generate with AI (`POST .../generate-metadata`) require the same origin and the strict effective owner: an admin must be acting as the user, and the internal and scanner keys are refused, because these skills enter that user's agent prompt and Generate spends that user's model keys. They are JSON only. Generate spends only the owner's own keys, on the model the owner chose, and never sends a skill whose text holds a key or token (an AWS key, a JWT, a private key...) to that model; its answer is a proposal re-validated by the webapp, saved only when the person uploads. Every skill write holds the per-user advisory lock (`webapp/src/lib/userSkillWrites.ts`), and a batch is saved whole or not at all.

**MCP Tool Plugins run nothing of a member's inside the agent.** A stdio MCP server runs its `command` as root in the agent container, which holds every tenant's data and the master secrets, so only an administrator's (role read from the database) is saved, tested or loaded: `POST /api/users/[id]/mcp`, `PUT .../mcp/[serverId]` and `POST /api/mcp/test` refuse a non-admin owner's stdio server with 403 `stdio_admin_only` (audited as `mcp_server.stdio_refused`), and every path that hands an owner's servers to the agent (the per-user reload, the agent's `?includeSkillContent=true` settings read) leaves a non-admin's out and logs `[rbac] stdio mcp server skipped user=<id> server=<id>`; a member's saved ones stay in their settings, shown as not run. The agent starts a stdio server through `env -i` with only its own `env` plus `PATH`, `HOME` and `LANG` (`mcp_registry.stdio_spawn_env`), never its own environment and never a `${VAR}` expanded, and so does the `/mcp/test` diagnostic re-spawn. No user's server may name `auth.token_env_var` (the agent resolved it from its own environment, so `INTERNAL_API_KEY` went to the server's URL): the webapp refuses it with 422 `token_env_var_refused`, and the agent ignores it on any non-system server and logs `[rbac] mcp token_env_var refused server=<id>`. `POST /api/mcp/test` acts on the caller's own account (a body `userId` must be one the caller may write), `POST /api/mcp/reload` is an admin's and never forwards its body (the agent's MCP toolset is shared), `GET /api/mcp/manifest` answers the caller's own servers masked, and the owner's raw servers and skill texts (`?includeSkillContent=true` on `GET /api/projects/[id]`) go to the master key only.

**A chat run spends only its own owner's credentials.** The agent is one process serving every user's runs. Each run is bound to the model client built from its own owner's providers: clients are cached by model id, a SHA-256 fingerprint of the provider rows and the owner (`agentic/orchestrator_helpers/llm_setup.py`, `LlmClientCache`), there is no shared client slot, and a run whose model cannot be built gets none, never another run's. Text-to-Cypher, Fireteam members and the tradecraft section picker use the run's client; `/guardrail/check-target` and `/tradecraft/verify` build the named user's own. The Tavily, SerpAPI and Shodan keys, their rotation pools and the tradecraft GitHub token are read at call time from the settings bound to the run's task (`agentic/tools.py`, `run_user_settings`), never written onto a shared tool: an empty key means none. The agent's user MCP toolset stays one per process, so a run whose owner's server set differs from the loaded one is refused with `mcp_toolset_busy` while another owner's run on a different set is live, and the reload a member's MCP save asks for is deferred in the same case (202, a save warning; the set loads at their next run); each refusal logs `[rbac] mcp toolset busy` (`agentic/mcp_toolset_guard.py`).

**Shell sessions are per project.** The Kali sandbox runs one `msfconsole` for every user, so its session list holds every user's sessions, background jobs and listeners. Each session is traced through the session manager's link to the chat whose run opened it, then to that chat's conversation and project: `GET /api/agent/sessions` returns the sessions and listeners of projects the effective user owns, each naming its project, and nothing about the others; the untagged ones, other projects' and every job need `shell_sessions_all` (an admin, the `shell_sessions` legacy grant, or the escape hatch for pre-upgrade accounts), judged on the signed-in account (`webapp/src/lib/authz/agentSessionsAccess.ts`). Interact and kill look their target up in that same view and answer 404 for anything else before the command reaches the console; each drive is audited (`agent.session_interact`, `agent.session_kill`, `agent.job_kill`: session id, project, how access was granted, never the command). The session manager forgets a session's chat link when the session closes or is killed and when `msfconsole` restarts, so a reused session number never shows under the previous session's project.

**Tenant-scoped deletion.** The Prisma schema ties child objects to their owning user/project with `onDelete: Cascade`, so deleting a tenant removes all of its data with no orphans.

**Plugin platform authorization (`webapp/src/lib/plugins/`).** Installing, updating, enabling, disabling, rolling back, uninstalling, reading logs and exporting a plugin's data are **instance-wide, admin-only** actions (`requirePluginAdmin`), and the admin role is **read from the database on every request**, not from the login token, which can outlive a demotion by up to seven days. A user's plugin job is visible only to its owner (404 otherwise). Plugin code is held to the same tenancy: every call token is bound to (plugin, acting user, project, session), and the Gateway re-checks the project's and session's tenancy on every call, so a plugin acting for one user cannot read another user's transcript or data.

## 8. Service-to-service authentication

Internal calls between components are authenticated with distinct, scoped, constant-time-compared keys. All of these are generated by `redamon.sh` (`ensure_auth_secrets`, `openssl rand -hex 32`, idempotent).

| Credential | Held by | Protects | Comparison |
|---|---|---|---|
| `AUTH_SECRET` | webapp | Login JWT + act-as cookie signing | jose verify |
| `INTERNAL_API_KEY` | webapp, agent | Webapp/agent internal endpoints | constant-time |
| `SCANNER_API_KEY` | scan containers | Opens nothing on its own: accepted only beside the scan's **job credential** (settings and project GET, traffic ingest, agent `/llm/*` and `/jev/*`), each bound to the credential's tenant or project; never the master key | constant-time |
| `ORCHESTRATOR_API_KEY` | webapp only | Every orchestrator route except `/health` | `hmac.compare_digest` |
| `MCP_AUTH_TOKEN` | agent | Every Kali server, Bearer: the MCP SSE ports, the Metasploit session manager (`:8013`), the Hydra progress stream (`:8014`), the terminal (`:8016`) | `hmac.compare_digest` |
| `AGENT_WS_TICKET_SECRET` | webapp (sign), agent (verify) | WebSocket tickets, kept separate from `AUTH_SECRET` so agent compromise cannot forge login cookies | `hmac.compare_digest` |
| `TUNNEL_AUTH_TOKEN` | webapp | Tunnel manager `:8015` `/tunnel/configure` | `hmac.compare_digest` |
| `PLUGIN_RUNNER_KEY` | webapp, plugin runner supervisor (never plugin workers) | The runner's API (`:7080`, through the proxy on `:7072`) and the runner's run list (`/api/plugin-runner/v1/run-list`) | constant-time |
| `PLUGIN_CALL_TOKEN_SECRET` | webapp only | Signs the per-call JWT plugin code presents to the Gateway, bound to (plugin, user, project, session) | jose verify |

**Key scoping is deliberate.** The orchestrator holds the real Docker socket, so its key is distinct from `INTERNAL_API_KEY` (which recon containers hold and could otherwise replay). Scanners receive only `SCANNER_API_KEY` and their scan's job credential, never the master key: with no scanner key configured the orchestrator refuses the start (503 `scanner_key_missing`, logged `[rbac] scanner key missing: run ./redamon.sh update to generate it`) rather than handing the container `INTERNAL_API_KEY`. The scanner key's route allowlist is narrow, but it was never a strict subset of what a scan needs: on its own it unmasked any account's settings and read or wrote any project. It now opens nothing alone. The webapp mints a **job credential** at every scan start (`webapp/src/lib/authz/machineCredential.ts`; the run credential's format, key `hmac(INTERNAL_API_KEY, "redamon-job-credential-v1")`, audience `scan`, the project's owner, the project, one start, 7 days); the orchestrator verifies it, admits the scan under its tenant rather than the request body's user, and hands it to the containers that call back as `REDAMON_JOB_CREDENTIAL`; they send it as `X-Redamon-Job` beside the key. `GET /api/users/[id]/settings` then reads only the credential's tenant, `GET /api/projects/[id]` and `POST /api/traffic/[projectId]/ingest` only its project, and the agent's `/llm/*` and `/jev/*` act for its tenant and project and refuse a body naming anyone else (`require_master_or_job_credential`). A refusal answers 403 or 401 with a `job_credential_*` code and logs `[rbac] job credential refused reason=<code>`. A credential copied out of a running scan container still works for that one tenant and project until it expires. The worker holds **neither** the master internal key, the scanner key nor the Neo4j credential: its two clients that call the agent back (`redagraph` in the terminal and the `proxy_brain` SDK) present a **run credential** the agent mints (`X-Redamon-Run`; `agentic/machine_credential.py`): an HMAC token under a key derived from `INTERNAL_API_KEY`, naming its audience (`graph` or `traffic`), one user and one project, and expiring (12 hours for a terminal connection, 15 minutes for a `proxy_brain` call). A terminal's credential is honoured only while that connection is open (the agent records its run on the socket; after it closes the answer is `run_credential_closed`), and a traffic credential only beside the `REDAMON_CTX` tag of the same user, project and run. The agent's `/graph/exec`, `/text-to-cypher` and `/traffic/*` take the master key or such a credential (`require_master_or_run_credential`), never the bare scanner key; with a credential the tenant comes from it, not from the body, and a refusal logs `[rbac] run credential refused reason=<code>`. The routes only the webapp calls (`/emergency-stop-all`, `/mcp/manifest`, `/mcp/reload`, `/mcp/test`, `/files`, `/models`, `/llm-provider/test`, `/tradecraft/verify`, `/guardrail/check-target`, `/graph/nl-query`, `/graph/schema-doc`, `/kali/toolbox`) take the master key only (`require_configured_master_auth`; the billed ones keep the LLM rate limit and daily cap behind it), so no agent route accepts the bare scanner key (`agentic/tests/test_scanner_key_scope.py` walks every route). On the webapp, the scanner key beside a session cookie grants nothing on a write: the capture-proxy settings of `PUT /api/users/[id]/settings` take an admin or the internal key. Every process the sandbox starts for a person or the agent (the terminal shell, `kali_shell`, `execute_code`, `proxy_brain`, `msfconsole` and every tool wrapper) gets an environment without `MCP_AUTH_TOKEN`, `TUNNEL_AUTH_TOKEN` or any `*_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD` (`mcp/servers/_safe_env.py`; `tests/test_kali_shell_env_scrub.py` fails on a spawn that does not use it). The plugin call-token secret is held by the webapp alone and must differ from `AUTH_SECRET`, `PLUGIN_RUNNER_KEY`, `INTERNAL_API_KEY` and `AGENT_WS_TICKET_SECRET`: the runner holds the runner key, so a runner escape must not yield the token key, and a leaked call token must never pass as a login (the middleware accepts any `AUTH_SECRET`-signed JWT carrying `sub` and `role`).

**Fail posture.** The orchestrator key, MCP bearer, tunnel token, WebSocket ticket, plugin runner key and plugin call-token secret **fail closed** (reject when their secret is unset). The runner key deliberately does not reuse the agent's `require_internal_auth`, which accepts every request when no key is set. The webapp/agent `X-Internal-Key` check fails open with a one-time warning **only** in a dev stack where the secret has not been generated yet, except on the agent routes that refuse for themselves without a configured master key and answer 503: the sandbox's run-credential routes (`/graph/exec`, `/text-to-cypher`, `/traffic/exec`, `/traffic/replay`, `/traffic/browser`), the scan containers' job-credential routes (`/llm/*`, `/jev/*`), `/graph/triage`, and the master-only routes behind `require_configured_master_auth`; a scan start without a configured master or scanner key is refused (503 `job_credential_unverifiable` / `scanner_key_missing`); `redamon.sh` generates all of them on install, and the deploy secrets gate refuses to boot the internet-facing posture without them. The webapp-side comparators and the agent's LLM guard also reject the literal `changeme`; the other Python service comparators rely on the deploy secrets gate to reject weak values (and the webapp never mints a ticket signed with `changeme`, so no valid weak ticket exists). The internal-key **route allowlist** is enforced only when `INTERNAL_KEY_ALLOWLIST_ENFORCE=true`; by default it is log-only (a valid internal key is currently accepted off-allowlist with a warning), while the scanner-key allowlist is always enforced.

**Header spoofing is blocked at the edge** (see [Section 4](#4-edge-hardening-nginx)): nginx strips `X-Internal-Key`, `X-Scanner-Key`, `X-User-Id`, `X-User-Role` inbound, so these headers are honored only from internal callers on the Docker network.

## 9. WebSocket security

The four agent WebSockets are the most powerful surface (they include `/ws/kali-terminal`, an interactive root PTY, and the two cypherfix sockets that clone repositories and edit code). Evidence: `agentic/ws_ticket.py`, `websocket_api.py`, `api.py`, the cypherfix `websocket_handler.py` files.

**Signed ticket.** Each `/ws/*` handshake requires a short-lived **HS256** ticket minted by the JWT-authenticated webapp, carrying `{ sub, pid, sid, aud }` (user, project, session, and the one socket it opens: `agent`, `kali-terminal`, `cypherfix-triage` or `cypherfix-codefix`) with a **60-second** expiry and 30-second verification leeway. The agent verifies it stdlib-only: it pins `alg=HS256` (rejecting `alg:none`), compares the signature with `hmac.compare_digest`, checks expiry, requires non-empty `sub`/`pid`/`sid`, and refuses a ticket without `aud` or with another socket's (logged `[rbac] ticket refused aud=<socket>`). **Identity is taken from the verified ticket claims, never from the self-asserted init frame**, which closes session hijacking. This fail-closed ticket applies to **all four** paths (close code 1008 when `AGENT_WS_TICKET_SECRET` is unset).

**Kali terminal.** The webapp mints a `kali-terminal` ticket only when the real signed-in account holds the terminal (an admin, a legacy `kali_terminal` grant, or the `REDAMON_SHARED_TOOLS_COMPAT` escape hatch), never through an act-as target's grant, and audits it as `agent.terminal_opened`; the terminal shows a permanent "shared environment" banner. The sandbox's terminal server (`:8016`) refuses every upgrade that lacks the `MCP_AUTH_TOKEN` bearer only the agent's proxy sends (fail closed when unset), before any PTY is forked, and runs the shell as the user and project the proxy took from the verified ticket, ignoring the browser's init frame. The proxy also hands the shell a 12-hour `graph` run credential for that user and project (in an upgrade header, never the query), which `redagraph` presents; when it expires `redagraph` says to reopen the terminal. The credential is honoured only while that connection is open: the proxy records its run on the socket, so closing the tab or `/ws/close` ends it.

**Closing open sockets.** A ticket is checked once, at the handshake. The agent's master-key `POST /ws/close` `{user_id?, project_id?, kinds[], scope?}` closes the matching open sockets (close 4403): `/ws/agent` from its session registry, stopping the run too (a run is matched by who started it, so one whose tab is closed is still stopped); the terminal and both cypherfix sockets from a registry each handler joins after its ticket check. A socket an admin opened while acting as a member rests on the admin's access: a close for the member's own access (`scope: access`, the default, such as a removed grant) leaves it open, while a close of either account (`scope: account`) or of the member's access to its project (`project_id`) ends it. No webapp route calls it yet, so a socket opened before access ends stays open until it closes on its own.

**Same-origin check.** A server-side origin check (a defense that CORS middleware does not provide for WebSocket handshakes) runs before the socket is accepted on `/ws/kali-terminal` and the two cypherfix sockets; `/ws/agent` relies on the signed ticket alone. Allowed origins default to the webapp origin and are configurable via `AGENT_CORS_ORIGINS` (never `*`).

**Anti-hijack and back-pressure.** A live session key cannot be taken over by an unverified peer (the collision is refused with close 1008 "session in use"), a verified reconnect inherits the running task and is identity-checked so a replaced connection cannot evict its successor, and new sessions past the memory-governed ceiling are refused with close 1013.

**CORS.** The agent's FastAPI `CORSMiddleware` is scoped to the webapp origin with `allow_credentials=False`, replacing an earlier wildcard that had allowed cross-origin drive-by reads.

## 10. Privilege separation and container-escape prevention

The target-facing worker is the least-trusted component and holds no secrets; a compromise there must not reach the host or the control plane. Evidence: `services/docker_broker/broker.py`, `docker-compose.yml`, `recon_orchestrator/container_manager.py`.

**Docker-socket broker.** Recon containers need to spawn tool containers, but mounting the raw `/var/run/docker.sock` would let a compromised container run `docker run -v /:/host --privileged` and own the host. They instead mount a **filtering broker** socket. The broker (`services/docker_broker/broker.py`, stdlib-only) holds the real socket and **blocks by default**: only the Docker API calls the tools' real `docker` invocations send are forwarded (the `_ROUTES` allowlist of method and path), and anything else (exec, archive, update, export, commit, build, image tag/push/delete/load, events, system calls) gets a 403 and one `DENY` log line before the daemon is contacted. `services/docker_broker/test_tool_invocations.py` replays every docker call site under `recon/` and `scanners/supply_chain_common/` through the broker and fails when a route, mount, writable volume or network is missing or unused. It validates every `create`, denying:

- `Privileged=true`; any capability outside `{NET_RAW, NET_ADMIN}`; device passthrough.
- Host or `container:` for `PidMode`/`IpcMode`/`UsernsMode`/`CgroupnsMode`, and `container:` network mode (host network is allowed, since raw/loopback scanning needs it); `VolumesFrom`; masked/readonly-path overrides; any `SecurityOpt` containing `unconfined`.
- Non-allowlisted images (a fixed allowlist of the shipped tool images, operator-extensible via env), enforced on both `create` and `docker pull`.
- Bind sources outside `/tmp/redamon` and three repository subdirectories (`recon/wordlists`, `mcp/nuclei-templates`, `scanners/supply_chain_common`, read-only, never a dot component below them, so never `.env` or `.git`), normalized first to defeat traversal, and any path touching the docker socket. The repository root comes from `DOCKER_BROKER_REPO_ROOT` (compose passes `${PWD}`); unset, no repository path can be mounted. Read-write binds only under `/tmp/redamon`.
- Named volumes outside the tool set, and a named volume mounted read-write unless it is writable: only `nuclei-templates` is (the template update writes it); the offline OSV database and the incident intel are read-only. Only the supply-chain analyzer's and the TruffleHog verifier's bridges can be inspected or created, as plain local bridges.

The broker also stamps a `redamon.broker-owned=1` label on everything it creates, **gates the verbs it allows on existing containers** (attach/start/wait/kill/stop/pause/unpause, logs, inspect, remove) to broker-owned containers only, and forces an ownership filter onto `GET /containers/json`, so a pivot cannot exec into infrastructure containers or even enumerate them. Denied requests never reach the real daemon (lazy upstream connect). It injects a 2 GiB memory cap on every tool container, caps request headers at 1 MiB and create bodies at 8 MiB, and forces `Connection: close` to prevent request smuggling.

**Capability scoping.** No container runs `privileged`. The Kali worker and the GVM scanner carry only `NET_ADMIN` + `NET_RAW` (raw sockets for SYN scans, tunneling); the previously-granted `SYS_PTRACE` was dropped. The kb-refresh sidecar runs `cap_drop: ALL`. Recon containers, formerly `privileged: true` (a full host-escape primitive), now request only `NET_RAW`. Note that spawned scan containers get `NET_RAW`-only plus the scoped scanner key but are not otherwise `cap_drop`ped or `no-new-privileges`; they are constrained by the broker, the pentest-net segment, and holding no master secret (see [Section 20](#20-documented-residual-risks)).

**Anti-persistence.** The worker's MCP server source is mounted read-only with `PYTHONDONTWRITEBYTECODE=1`, so worker RCE cannot trojanize a server file for restart-surviving persistence.

**Network segmentation.** Three bridge networks plus a per-job isolated one:

- `redamon-network`: webapp, agent, kali-sandbox, postgres, neo4j.
- `redamon-orchestrator-net` (isolated, pinned subnet): recon-orchestrator and the on-demand Ollama judge, with the webapp multi-homed in as the **only** legitimate caller. The worker cannot reach the privileged orchestration API (`:8010` is also loopback-bound).
- `pentest-net`: kali-sandbox and spawned scanners (target-facing plane).
- `redamon-codefix-net`: created on demand for the CodeFix build sandbox; it has NAT egress but **no RedAmon peer**.
- `redamon-plugins-net` and `redamon-plugins-edge`: both `internal` with `gateway_mode_ipv4: isolated` and fixed subnets (`10.213.80.0/24`, `10.213.81.0/24`). The plugin runner sits on the first alone with the plugin-gateway proxy; the proxy and the webapp share the second. See the plugin runner below.

**CodeFix build sandbox.** Building an operator's GitHub repo can execute attacker-influenced code (malicious `postinstall`, prompt-injected build steps). That build/test runs in an ephemeral, per-job sandbox container: **empty environment (no secrets)**, `cap_drop=ALL`, read-only root filesystem, non-root user, setuid/setgid stripped from the image, memory/CPU/PID limited, a size-capped `/tmp` tmpfs as the only writable path, on the isolated network, with `.git` mounted read-only. It is driven via `docker exec` through `agent -> webapp -> orchestrator` (each hop authenticated), so the agent gains no new reach. The GitHub token is supplied via `GIT_ASKPASS` (never in the clone URL or `.git/config`, never entering the sandbox), git hooks are disabled, commits stage only approved files (no `git add -A`), and pushes to `main`/`master`/default are refused. A TTL reaper tears the sandbox down.

**Plugin runner (`services/plugin_runner/`, `docker-compose.yml`, `docker-compose.plugins.yml`).** The plugin platform runs on every install and runs third-party code, so it is contained as hostile without relying on the plugin to use the SDK:

- **One process and one UID per plugin version.** The supervisor starts each worker with `python -I -S` (no site packages, no user path, no environment-driven imports) and a clean environment holding no database credential, LLM key or runner key, only a per-call token. Workers run at `nice 10`.
- **No way out but one door.** The runner's only network is `redamon-plugins-net`, shared with the `plugin-gateway` proxy and nothing else: no internet, no address on the host (`gateway_mode_ipv4: isolated`). The proxy (standard library only, `gateway_proxy/proxy.py`) forwards only `/api/plugin-gateway/v1/*` and `/api/plugin-runner/v1/*` to the webapp and only `/runner/v1/*` back to the supervisor, and strips every header but four. Before anything goes upstream it refuses any method but GET or POST, any %-encoded byte, `..`, `//` or backslash, a query string on a POST or over 512 characters, a body on a GET, a chunked body and a body over 8 MB; each listener has its own connection cap, so plugin code cannot starve the webapp's door. It never joins `redamon-network`, where a compromised proxy would reach Postgres, Neo4j and the agent's body-identity routes.
- **Code is read-only to plugins.** The plugins volume is mounted read-only into the runner; only the webapp's Plugin Manager writes it, so a plugin cannot change its own code or another plugin's.
- **Container hardening.** `read_only` root filesystem, `cap_drop: [ALL]` with only `SETUID`/`SETGID` (to start workers under their UIDs) and `KILL` (to stop them), an `init` as PID 1 that reaps what a killed plugin leaves behind, setuid/setgid bits stripped from the image, and `mem_limit`/`pids_limit`/`cpus`. Like the other hardened services it omits `no-new-privileges`, which stops every container from exec'ing on the reference host. The proxy is `read_only`, `cap_drop: [ALL]`, 128 MB.
- **Plugins only propose.** A plugin changes agent behaviour only through skill-text proposals that a person approves in core UI (see [Section 13](#13-agent-safety-controls)), and its model calls are made by the agent with the user's own key, so no plugin ever holds a provider key.
- **Refused, never degraded.** The platform cannot be switched off, so its containment is a precondition of running at all: `install`, `update` and `up` check Docker Engine 28.0.0 or newer before building anything, then the plugin secrets, the runner image and Docker's acceptance of the plugin networks, volume and containers before any core service is (re)created, and stop with the reason when one fails. A plain `docker compose up -d` loads no overlay and starts neither plugin service, so every plugin action fails until `./redamon.sh up`.

## 11. SSRF and egress control

Two complementary guards, tuned to opposite trust stances.

**Untrusted-target fetches (`agentic/orchestrator_helpers/fetch_guard.py`; and `recon/main_recon_modules/ip_filter.py`).** When the agent or recon fetches web content from a target (tradecraft crawl, redirects, URLs probed from a target's JavaScript), the destination is resolved via `getaddrinfo` and **every** resolved IP must be public: loopback, RFC1918 private, link-local (which covers the cloud-metadata `169.254.169.254`), reserved, multicast, unspecified, cloud-metadata hostnames, and CGNAT `100.64.0.0/10` are all rejected. IPv4-mapped IPv6 is judged on the embedded v4 address so encoding tricks cannot bypass it. Only `http`/`https` schemes are allowed.

Tradecraft fetches apply this policy where it counts, at connect time: `pinned_async_transport()` resolves, judges and dials the judged address in one step for every connection, redirect hops included, so they have no rebinding gap (CVE-2026-111323). A refused fetch is never retried in the Playwright browser. The browser fallback runs a guard script that aborts navigations and page resources aimed at internal addresses and withholds any page whose redirect chain crossed one; Chromium follows HTTP redirects before the script can see them, so a redirect hop can still send a blind request inward, but its response never comes back.

**Operator custom LLM endpoints (`agentic/orchestrator_helpers/llm_url_guard.py` and `webapp/src/lib/llm-url-guard.ts`).** Operators may point a provider at a custom `baseUrl`, so this guard preserves self-hosted models (localhost, RFC1918, Docker-service hosts pass) while rejecting the narrow never-legitimate set: the AWS/GCP/Azure metadata IP `169.254.169.254`, ECS `169.254.170.2`, Alibaba `100.100.100.200`, AWS IPv6 `fd00:ec2::254`, and `metadata.google.internal`/`metadata.goog`, plus all link-local. Because it resolves through the same `getaddrinfo` the client uses, integer/hex/octal IP encodings and IPv4-mapped IPv6 normalize and are caught. Disabling TLS verification (`sslVerify=false`) is refused for any host that resolves to a public IP (the MITM exposure of a Bearer key + prompt over a TLS-off public connection), while still allowed for private/internal self-signed endpoints.

**OpenAPI document fetches (`recon/helpers/openapi/fetch.py`, `is_address_safe_to_scan` in `recon/main_recon_modules/ip_filter.py`).** Recon downloads API specification documents and follows their redirects and `$ref`s on the same origin only, inside the project scope. Before every hop it applies the pipeline's rule for discovered names rather than the untrusted-target rule above: a host the operator typed (the target domain and its subdomain prefixes, Domain-batch hosts, configured or custom document URLs, target IPs and CIDRs) is fetched whatever it resolves to, as `recon/main.py` does for operator-supplied hosts and IP mode does for its targets. Any other host is resolved and refused when it is a cloud-metadata name, when any address is loopback, link-local, unspecified or multicast (IPv4-mapped IPv6 judged on the embedded v4), or when it does not resolve; the refusal sends nothing and reports `blocked_address`. Private and CGNAT addresses stay allowed, because recon scans internal estates on purpose. This matters because recon runs on the host network, where the agent API serves `/openapi.json`, one of the default discovery paths. OpenAPI never calls a declared operation. Later scanners request an endpoint known only from a specification with GET or HEAD only. Nuclei templates send their own requests to such an endpoint, as to any other target URL.

Outside tradecraft, these guards resolve the host and then hand it to the HTTP client, which re-resolves at connect time; that resolve-then-connect gap (DNS-rebinding TOCTOU) is a documented residual.

**Workspace URL import and website mirror (`agentic/workspace_import/`).** A user can import a repository, a file, an archive or a whole website into the Agent Workspace. Every request goes through one guarded fetcher (`fetch.py`): `pinned_async_transport()` on every connection, redirects followed by hand (at most five) with `assert_safe_fetch_url` on every hop, and bodies streamed to disk under real byte caps. A link with a user name or password in it is refused, and the user's GitHub token is attached only on https hops to an exact GitHub host, never to codeload, whose links carry their own temporary token. A plain git link is cloned with its checked address pinned (`http.curloptResolve`), redirects off and a watchdog. A website mirror also runs a hop policy on every request it sends (pages, assets, redirect hops, robots.txt, the sitemap). That policy refuses government, military, education and intergovernmental domains (the hard guardrail), refuses the hosts the project's Rules of Engagement exclude, keeps pages under the seed's host and folder, and keeps a gap between requests to one host. The RoE settings are loaded for that project alone, and a mirror whose settings cannot be loaded fails closed. Every request to a target, also an asset that a copy of another site links to, keeps the engagement window (checked again on every request: a copy of a target stops when the window closes, a target asset of another site's copy is skipped), the RoE rate cap and stealth's one request a second. A seed inside the project's scope is also refused outside the window, and stealth runs its copy one request at a time. The only request sent before these checks is the preview's classification probe, one GET of the link; a site root on a protected host is refused before even that. `WORKSPACE_URL_IMPORT_ENABLED` turns URL import off. Imports never use a browser.

**Plugin downloads and plugin egress (`webapp/src/lib/plugins/fetchRemote.ts`).** The webapp downloads the plugin catalog and archives only over `https` from an allowlist of GitHub hosts (`github.com`, `raw.githubusercontent.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`; `PLUGINS_DOWNLOAD_HOSTS` to change it), re-checking the host on **every** redirect hop (at most five) and capping the archive at 20 MB, so a catalog entry cannot point the webapp at an internal address. Plugin code itself has **no egress**: the plugins network is `internal`, and plugin screens run under a CSP that allows no remote connection or image (see [Section 12](#12-injection-and-input-validation-defenses)).

## 12. Injection and input-validation defenses

**Uploaded and imported archives (`agentic/workspace_import/extract.py`).** A zip or tar from a user or a URL is never handed to `extractall`. Each entry is written by hand, opened relative to its own folder with `O_NOFOLLOW`, so no entry can write outside the destination or through a link. A path that leaves the folder (absolute, `..`, NUL) refuses the whole archive. Links, devices and pipes are skipped. The size and entry caps count the bytes really written, not what the archive declares. A mirrored site cannot write the mirror's own `.import.json` or `_manifest.jsonl`, and every path segment it sends is neutralized before it becomes a file name.

**SQL injection.** All relational access goes through the Prisma query builder (parameterized). There is no `$queryRawUnsafe`/`$executeRawUnsafe` in production code; the few tagged-template raw queries are parameterized and test-only.

**Cross-site scripting.** The UI is React (auto-escaping); the only `dangerouslySetInnerHTML` uses are static constants, and there is no `eval`/`new Function` in production. The nginx CSP is a second layer in the hardened posture.

**Prompt injection from hostile tool output.** The agent reasons over tool output from hostile targets, so every untrusted value is wrapped in a **per-call random-nonce sentinel** the target cannot predict (`agentic/prompt_safety.py`), with a standing instruction to treat marked regions as data only and look-alike markers neutralized. This covers the ReAct trace/chain formatters, think-node and fireteam tool-output sections, execution-chain preview lines, cypherfix, the report summarizer, and tradecraft, closing the "close-the-fence and forge a SYSTEM directive" escape.

**Graph write protection (`graph_db/tenant_filter.py`).** The worker-facing `/graph/exec` proxy is read-only: a write-clause regex rejects CREATE, MERGE, DELETE, DETACH DELETE, SET, REMOVE, DROP, ALTER, LOAD CSV, GRANT/DENY/REVOKE, database admin, and write procedures including `apoc.create/merge/refactor/periodic/trigger/schema/atomic`, `apoc.cypher.runWrite/doIt`, and `dbms.*`. Combined with the tenant filter and the removal of the worker's Neo4j credential, a compromised worker drops from "master read+write on all data" to "read-only, tenant-scoped reads."

**Workspace path traversal (`agentic/workspace_fs.py`).** Project ids are validated (rejecting `/`, `\`, null byte, leading `.`/`..`) so `projectId=../etc` cannot escape the workspace root; protected-subdir checks normalize with `os.path.normpath` first; archive/download skips symlinks so a workspace symlink to `/etc/passwd` cannot be served inline.

**Archive extraction.** `fs_extract` validates every member path against the destination and enforces entry/byte caps (5,000 entries / 500 MB); project import checks central-directory sizes before decompression; Knowledge Base curation uses a bounded, path-checked tar iterator and never calls `extractall`.

**Upload validation.** Uploads are extension-allowlisted, size-capped (wordlists 50 MB, Nuclei templates 1 MB, JS recon 10 MB, RoE docs 9 MB, project import 100 MB), filename-sanitized (`path.basename` + charset strip, `PROJECT_ID_RE`), and content-validated where it matters (Nuclei templates parsed for a valid `id:`, JSON uploads parsed, RoE documents type-allowlisted and page-capped). The RoE cap sits under Next's 10 MB proxy body limit, which truncates a larger body silently, and `Content-Length` is checked before the body is parsed.

**RoE documents are parsed in isolation (`webapp/scripts/roe-extract.mjs`, `lib/roe/extractText.ts`).** pdfjs and mammoth run in a child process with no environment beyond `NODE_ENV` (no database URL, no secrets), a 256 MB heap, `--disallow-code-generation-from-strings`, an RSS watchdog and a 30 s kill; pdfjs runs with `isEvalSupported` and font loading off. A DOCX is proved to inflate to at most 50 MB and 2,000 parts (each entry is inflated with a `maxOutputLength` budget, so a lying central directory fails too) before mammoth sees it. A crash or a timeout is a fixed `extract_failed` message that never quotes the document.

**A RoE document is untrusted configuration (`recon_settings/registry.yaml` `roe_parse`, `lib/reconSettings/roeParse.ts`).** A parsed document may never set scope (`create_only`), the agent's system prompts, LHOST/LPORT, callback and resolver hosts, tunnels, the model, repositories or credentials (`roe_parse: deny`, absent from the parse catalogue), and may set the approval and confirmation gates, the guardrail, tunnels, Kali installs and post-exploitation only to their safe value (`tighten_only`). A registry test fails when an agent or free-form field has no class. Every value is re-validated, the stored text is the server's own extraction, the stored parse is rebuilt on the server (a planted `applied.targetDomain` from a client or an imported bundle is dropped), and a replace is recomputed server-side and must equal what the person confirmed. The agent and webapp must be built from the same registry: the parse route refuses an agent whose prompt digest differs (`agent_registry_outdated`).

**Tool images are fixed (`recon/project_settings.py`).** Recon passes `*_DOCKER_IMAGE` values to `docker run`, so none of them is a project setting: there is no column, form field, preset key or MCP write for one, and the settings chokepoint pins every key to the image RedAmon ships for that tool, so an injected `attacker/evil:latest` cannot become arbitrary host container execution. The docker-broker independently enforces its own image allowlist as a second, non-identical gate.

**Plugin archives and plugin input (`webapp/src/lib/plugins/`).** Unpacking a plugin archive rejects absolute paths, `..`, links and oversize archives before anything reaches the plugins volume. Every Gateway route accepts JSON only (`415` otherwise) with bounded bodies, nesting and container sizes, and plugin data is held to per-plugin quotas (`PLUGIN_DATA_MAX_ROWS`, `PLUGIN_DATA_MAX_BYTES`, `PLUGIN_DATA_MAX_VALUE_BYTES`, `PLUGIN_DATA_MAX_ROWS_PER_OWNER`). The user-facing `/api/plugins/*` routes accept only same-origin JSON (`PLUGINS_ALLOWED_ORIGIN` behind a reverse proxy), so a cross-site form cannot drive a plugin action or an approval. Plugin screens on `/plugins` and `/plugins/*` get their own CSP (`default-src 'self'`, `img-src 'self' data: blob:`, `connect-src 'self'`, `frame-ancestors 'none'`); plugin text shown elsewhere goes through `SafeMarkdown` and React escaping, every plugin contribution carries a plugin badge, and its icons come from an allowlist, so a plugin cannot pass itself off as core UI. A transcript handed to a plugin has credential-shaped values (keys, tokens, cookies, private keys) masked together with their key.

**Orchestrator input trust (`recon_orchestrator/api.py`).** The orchestrator no longer trusts a client-supplied `webapp_api_url`; all credentialed calls use server-controlled URLs, so a caller cannot redirect the internal key to an arbitrary host.

**Provider keys never reach recon logs (`recon/helpers/circuit_breaker.py`).** Recon stdout streams into the webapp's log drawer, so the circuit breakers that pause a failing data provider are built to log the provider, endpoint and outcome only — never the API key and never a response body. A refused key is reported by its **1-based position** in the rotation, not its value; a provider whose error text can echo the submitted key (e.g. Netlas' `400 ... api key`, an NVD `message` header) is classified from the status and a fixed marker, with the body discarded. The key material stays in the scan container's environment and is never written to a finding, a log line or the graph.

## 13. Agent safety controls

The autonomous agent is powerful (it drives offensive tools against live targets), so it carries its own layered safety stack independent of the network controls above.

**Non-disableable hard target guardrail (`agentic/orchestrator_helpers/hard_guardrail.py`).** A deterministic block (no LLM, no network, no settings dependency, **cannot be toggled off**) refuses government, military, education, and international targets. It matches by TLD suffix (`.gov` and its national variants, `.mil`, `.edu`/`.ac.<cc>`, `.int`, and similar government patterns) and by an exact-domain frozenset of roughly 190 intergovernmental organizations on generic TLDs (UN system, EU institutions, development banks, tribunals, arms-control and standards bodies, Red Cross, and more), including their subdomains. It is enforced in **three independent tiers** that share no settings flag: project creation (webapp), scan launch (orchestrator), and agent reasoning (agent).

**LLM soft guardrail (`agentic/orchestrator_helpers/guardrail.py`).** A second tier classifies the target with an LLM and blocks major technology, cloud, social, financial, media, education, and government properties, reverse-resolving public IPs to hostnames first, while auto-allowing private/RFC1918 targets. It runs after the hard guardrail, is fail-closed at agent startup, and is operator-toggleable (`AGENT_GUARDRAIL_ENABLED`, default on).

**Phase gating.** Tools are bound to agent phases (`TOOL_PHASE_MAP`) and enforced at both selection and job-spawn time; classification fails safe to the least-privileged `informational` phase. A tool cannot run outside the phase it is authorized for.

**Human-in-the-loop for dangerous tools.** A `DANGEROUS_TOOLS` set (17 tools) is gated by `REQUIRE_TOOL_CONFIRMATION` (default on): the agent pauses for explicit operator approval before executing them, and fireteam members escalate the same confirmation with a bounded auto-reject timeout. Phase upgrades into exploitation / post-exploitation are likewise held for operator approval.

**Emergency stop.** The PAUSE ALL button stops agent runs together with their in-flight tools. For an administrator it is the instance-wide kill-switch (`/emergency-stop-all`, every user's runs); for a member it stops only that member's own runs (the master-key `/agent-sessions/stop-for`, which matches the user a run's session key names, so a run an administrator started acting as the member is the member's), and the answer and the button's tooltip say which. Each press writes an `agent.emergency_stop` audit row (scope, count). CypherFix triage and CodeFix runs are not agent runs and are not stopped by it.

**A RoE document cannot instruct the agent.** The document's raw text is not injected into any agent prompt; its terms reach the agent only through validated columns, and the two free-text record fields (notes, incident procedure) appear last, capped at 2,000 characters each, fenced with backticks neutralised, in a block that says they cannot change scope, tools, approvals or phases (`agentic/prompts/base.py`). Replacing a RoE that widens a third-party engagement is refused until an authorization is recorded. A schedule has no fingerprint guard, so a widening replace pauses every enabled schedule, and a narrower window or end date pauses the ones it would fail; a replace while a scan of the project runs is refused rather than half-applied.

**Rules of Engagement.** Scan launch is gated server-side by an RoE pre-flight (target scope plus a strict time-window check) against the trusted webapp URL; active/adversarial modules (web cache poisoning, AI Gauntlet, and others) are off by default and RoE-gated. Note that at agent-reasoning time the RoE time window is currently advisory (a prompt warning), not a hard block; the hard guardrail is the non-bypassable layer.

**A plugin cannot change the agent's instructions on its own.** The one plugin output that reaches agent behaviour is a proposed replacement for a part of a built-in skill (`sdk.override.propose`). The agent's scope rules are prompt text in the same instruction stream, so a proposal is **inert until a person approves it in core UI**: the review shows the before/after text with risk flags on lines that send data out, name a URL or host, or tell the agent to drop a scope, RoE or confirmation guard, plus the plugin's badge, and asks for confirmation. It is validated on propose and again on read, capped in growth (`PLUGIN_SKILL_TEXT_MAX_GROWTH`, 1.5× the factory size), turned Stale when its factory text changes, and resettable at any time; every active override is visible in the skill's version list. A disabled or uninstalled plugin's overrides stop applying from the agent's next turn. The hard guardrail above is code, so no override can reach it.

**An outside brain never approves its own actions (Agent in the Loop).** With `AGENT_IN_THE_LOOP_ENABLED=true` a person may pick `loop/mcp` as a chat's model: every model call then becomes a step that the person's own MCP client (Claude Code, Codex) answers with an `agent:loop` token. RedAmon keeps the loop, the tools and every gate. In such a run dangerous tools ask the person while `REQUIRE_TOOL_CONFIRMATION` is on; the person may turn it off for an unattended run, which the chat drawer marks with a red risk icon next to the Agent in the Loop chip; no MCP tool can answer an approval, a question or a confirmation; a token that drives a run holds no write or exec scope besides `agent:loop` (`loop_token_too_broad` otherwise), so a prompt injected through target text cannot turn the driver against RedAmon's other write tools; MCP writes, presets, imports and user defaults never select a loop model; the agent's own Cypher runs in a read-only Neo4j session; and every builder outside a chat run refuses a loop model. Steps carry no provider key, and the `loop_status` frames carry no prompt or answer text. Step prompts do carry target data to the person's client, which is the same trust the person already gives a provider.

**Reverse-shell exposure is opt-in and fails closed.** Port 4444 is loopback-bound in the hardened posture. Catching a direct reverse shell requires scoping `REVSHELL_TARGET_CIDRS` to the engagement targets and running `deploy.sh revshell-open`, which starts a transient host `socat` forwarder and opens ufw only to those CIDRs. A host reboot drops the forwarder, so the exposure **fails closed**; `revshell-close` tears it down.

## 14. Secret management

**Generation and rotation (`redamon.sh`).** All service secrets are generated with `openssl rand` on install, idempotently (append-if-absent). Database passwords are handled with care (`ensure_db_secrets`): on a fresh install a strong password is generated *before* the volume initializes; on an existing volume still on a legacy default, the live database is rotated in place (Postgres `ALTER USER`; Neo4j `ALTER CURRENT USER SET PASSWORD FROM ... TO ...`, the Community-safe self-service form) and the new value is written to `.env` **only after** the rotation succeeds, so a failure leaves no split-brain lockout. Compose refuses to start with unset DB passwords via `${POSTGRES_PASSWORD:?}` / `${NEO4J_PASSWORD:?}`.

**Secrets gate (deploy, `modules/secrets_gate.sh`).** Before exposing a host, the deploy verifies eleven secrets (`AUTH_SECRET`, `INTERNAL_API_KEY`, `SCANNER_API_KEY`, `ORCHESTRATOR_API_KEY`, `MCP_AUTH_TOKEN`, `AGENT_WS_TICKET_SECRET`, `TUNNEL_AUTH_TOKEN`, `PLUGIN_RUNNER_KEY`, `PLUGIN_CALL_TOKEN_SECRET`, `POSTGRES_PASSWORD`, `NEO4J_PASSWORD`) and **fails the build** if any is empty, a known default (`changeme`, `redamon_secret`, ...), or shorter than 24 characters.

**Plugin secrets (`redamon.sh`).** `PLUGIN_RUNNER_KEY` and `PLUGIN_CALL_TOKEN_SECRET` are generated like the others, when missing or empty. Before any core service is created or recreated, `redamon.sh`'s plugin preflight stops `install`, `update` and `up` (naming the reason, which `./redamon.sh status` repeats) when either is empty or `changeme`, when the call-token secret is shorter than 32 characters or equals `AUTH_SECRET`, `PLUGIN_RUNNER_KEY`, `INTERNAL_API_KEY` or `AGENT_WS_TICKET_SECRET`, or when `INTERNAL_API_KEY` is unset or `changeme`; the stack is not started with the plugin platform missing. The webapp enforces the same rules at runtime, and in the public posture the deploy secrets gate above also checks both.

**The GitHub token in workspace imports.** The browser never sends it: the web app reads the user's own `githubAccessToken` on the server for each GitHub import and never logs or returns it. An admin acting as a user imports with no token at all, because the user's token would open their private repositories to the admin, and the admin's would put the admin's repositories into the user's project. An import's provenance record (`.import.json`) is signed with a key derived from `INTERNAL_API_KEY` and bound to its project; rotating that key leaves existing imported folders unsigned, so they lose Re-sync and drop out of the agent's list of imported sources.

**Log redaction (`agentic/logging_config.py`).** A redaction filter on every log handler scrubs token shapes (GitHub PAT/OAuth/fine-grained, OpenAI `sk-`, Slack `xox*`, Bearer tokens, `authorization`/`api-key`/`token` key-value pairs, `user:pass@` in URLs, AWS `AKIA...`) to `[REDACTED]`. Harvested secret values are no longer printed to secret-hunter stdout, and the LLM-provider test returns a generic error.

**Secrets in transit at deploy time (`deploy.sh`).** The deploy config (`deploy.env`, carrying `AUTH_SECRET`, all API keys, DB and admin passwords) and any provided TLS keys are shipped mode 600 and are `shred -u`'d and removed on **every** exit, including error paths. The sudo password is passed out-of-band via `SUDO_ASKPASS`, never on a command line or visible in `ps`.

## 15. Denial-of-service and resource governance

**Workspace uploads and imports.** Each upload or import is capped at 2 GiB (`WORKSPACE_IMPORT_MAX_BYTES`) and 50,000 entries, and is refused when it would leave less free disk than the recon scan floor plus 1 GiB (before any byte is written when its size is known, otherwise as soon as it would cross that line), so it can never starve the scan dispatcher. At most four run at once on the server, and two per project for URL imports; their extraction, hashing and archive work runs on its own two-thread pool, never on the event loop's default pool. Extraction grows the reservation as it writes, because an archive's size says nothing about what it extracts to. A source that sends less than 64 KiB in a minute is dropped as not answering. A website mirror also stops at its page, depth, 500 MB and 30-minute limits (in-flight requests included), queues no more pages than its limit and at most 20 assets per page, and converts each PDF in a child process it kills after 60 s. Idle upload sessions are swept every 5 minutes.

RedAmon runs heavy concurrent scans and agent sessions on one host, so resource exhaustion is a first-class DoS concern.

**RAM-aware governor (`graph_db/resource_governor.py`).** A dual-cap system: every RAM-heavy knob keeps its configured ceiling **and** gains a second cap derived from live available memory (read from `/proc/meminfo`, VM-aware). Concurrency parameters scale down under pressure; per-unit allocations use a measured byte budget; reductions are logged with a `[RESOURCE-CAP]` marker. It fails open (to the configured cap) when memory is unreadable.

**Admission ledger (`recon_orchestrator/admission_ledger.py`).** Scans are admitted only within a **global concurrent ceiling** and a **per-user ceiling** (per-user default 10; global default 20 via compose) and only while their summed memory envelope fits a global budget; excess is refused with a typed reason rather than an OOM. Reservations are released on every termination path and reconciled against live containers so a crashed scan cannot leak its reservation into a self-DoS.

**Per-container caps.** Every long-lived service has `mem_limit`, `pids_limit`, and `cpus` in `docker-compose.yml` (with Neo4j's JVM heap sized under its mem_limit); every spawned scan container gets a CPU cap (scaled to cores), a fixed **512** PID cap (fork-bomb ceiling), and a memory cap; every broker-spawned tool container gets a 2 GiB memory cap injected. A startup RAM gate refuses to boot an undersized host (an ~8 GB floor derived from the service baseline plus OS headroom).

**Plugin limits.** A plugin cannot exhaust the host or other users: each worker is capped in address space (`PLUGIN_WORKER_MEM_MB`, 512) and processes/threads (`PLUGIN_WORKER_NPROC`, 64) and killed at the action timeout (`PLUGIN_ACTION_MAX_TIMEOUT`, 900 s); a plugin runs at most `PLUGIN_MAX_CONCURRENT_ACTIONS` (4) actions at once; a call token makes at most `PLUGIN_GATEWAY_CALLS_PER_TOKEN` (600) calls; plugin LLM calls have their own daily cap (`PLUGIN_LLM_DAILY_CALL_CAP`, 100), separate from the user's shared one; plugin data and transcripts are quota- and size-capped. The runner container's memory is sized by the RAM governor, its `cpus` clamped to the host's cores, and its PIDs capped (`PLUGIN_RUNNER_PIDS`, 256); its logs rotate at 10 MB × 3.

**Decompression and upload caps.** Project import and the agent's `fs_extract` cap zip/tar/gz decompression, and a RoE DOCX is held to a 50 MB inflate budget in a child process killed at 30 s; uploads are extension-allowlisted and size-capped (see [Section 12](#12-injection-and-input-validation-defenses)).

**Rate limiting.** The billed LLM endpoints carry a per-key token bucket (default 60 burst, 1/s refill) and a per-user daily call cap (default 5000), returning 429 (`agentic/llm_guard.py`). The edge adds nginx `limit_req`/`limit_conn` and slowloris timeouts ([Section 4](#4-edge-hardening-nginx)).

## 16. Audit and non-repudiation

Evidence: `webapp/src/lib/audit.ts`, `webapp/prisma/schema.prisma`.

Two **append-only** tables record security-relevant events. `AuditLog` (`audit_log`) stores `actorId`, `action`, `targetType`, `targetId`, before/after JSON, and a `source` (api/ui/admin/system), indexed for lookup by target and by actor. `ActAsAudit` (`act_as_audit`) records admin impersonation with `event` = `start`/`end` as **separate inserts** (an end is never an in-place update, preserving the trail). Actor columns are nullable so existing rows need no backfill. Audited `AuditLog` actions: authentication (`auth.login.success`, `auth.login.failure`, `auth.login.lockout`, `auth.logout` with the account that signed out); user administration (`user.create`, `user.update` with the name and email before and after, `user.role_changed`, `user.delete` with the email, role, owned project count and the projects deleted with the account, `user.delete_failed` when a project's teardown stopped the deletion (the account is kept; the row names that project, the failed step and the projects already deleted), `user.password_changed` for one's own password, `user.credentials_reset` for another account's; the host scripts write `user.create`, `user.role_changed` and `user.credentials_reset` with source `system`); every MCP write and a denied MCP call (`mcp.start_recon`, `mcp.start_recon.refused`, `mcp.stop_recon`, `mcp.update_recon_settings`, `mcp.create_project`, `mcp.attach_authorization`, `mcp.set_finding_verdict`, `mcp.submit_finding_review`, `mcp.start_triage_run`, `mcp.stop_triage_run`, `mcp.auth.denied`); Priority Board decisions and reviews (`triage.verdict` with the real actor behind an act-as session, `triage.review` with a SHA-256 of the review's text and never the text); triage runs (`triage.start` with its trigger, token, budget and model, `triage.finish`, `triage.finish.late`); and Mute Rules, which decide what the operator and the agent can see (`node_filters.saved`, naming a loaded preset, `node_filters.mode_changed`, `node_filters.applied`, `node_filters.apply_finished`, `node_filters.armed`, `node_filters.disarmed`, `node_filters.exemptions_cleared`, `muted_nodes.muted` for a single mute from the app or a mute over MCP, and `muted_nodes.unmuted` with what had muted each finding); and the plugin platform, where every lifecycle operation and override decision leaves a row (`plugin.install`, `plugin.install_failed`, `plugin.update`, `plugin.rollback`, `plugin.enable`, `plugin.disable`, `plugin.uninstall`, `plugin.purge`, `plugin.export`, `plugin.permissions_granted`, `plugin.revoked`, and `plugin.override.propose`, `.approve`, `.reject`, `.withdraw`, `.reset`, `.stale`, `.delete`); the Agent Workspace (`workspace.upload` when an upload is committed, `workspace.import` and `workspace.resync` when a URL import starts, with its kind, destination, name, the redacted link and whether a GitHub token was used); and the Rules of Engagement (`roe.parse` with the document's name, SHA-256, size, model and outcome, never its text or contacts; `project.roe.replace` and `project.roe.remove` with both documents' text digests, the changed keys and the paused schedules; `project.roe.download`), each carrying the admin behind an act-as session. Impersonation (act-as start and end) goes to `ActAsAudit`; the end row names the account acted as, and an end with no act-as cookie writes nothing. User-administration, logout and single-mute rows name the real signed-in account as the actor and add `actingAsUserId` while an admin acts as someone. Mute Rules rows record the real actor behind an act-as session. Writes are best-effort so a logging failure never breaks a request, and never record passwords or hashes. In the deploy posture the real client IP is trustworthy because `TRUST_PROXY` marks the nginx-supplied `X-Forwarded-For` authoritative.

## 17. Supply-chain integrity

**Pinned build sources.** The recon image and the git-cloned tools in the Kali image build from **pinned commits or release tags** (for example jsluice, ffuf `v2.1.0`, masscan, subjack, SecLists, jwt_tool, graphql-cop, sstimap, tplmap, phpggc, smuggler, h2csmuggler, clairvoyance, chisel, the PEASS-ng suite), so a moved upstream reference fails the build loudly. The Docker CLI and Docker Engine are installed from Docker's official GPG-verified APT repository. (A subset of the Kali image's Go-installed tools still tracks `@latest`/`@master`; pinning them is a tracked supply-chain follow-up, see [Section 20](#20-documented-residual-risks).)

**Knowledge Base feed pinning.** KB feeds are pinned to immutable upstream commits with per-feed sha256 (fail-closed), NVD responses are schema-validated, and the embedder/reranker revisions are pinned.

**Deploy patch integrity.** The single remaining deploy-time source patch is verified against an expected **sha256** and is **fatal on mismatch**; the two earlier patches were folded into the base app and dropped.

**Image allowlisting** (see [Section 12](#12-injection-and-input-validation-defenses)) prevents substitution of tool images at run time.

**Signed plugin catalog (`webapp/src/lib/plugins/keyring.ts`, `catalogVerify`, `docs/readmes/README.PLUGINS.md` §6.4).** Plugins are third-party code, so nothing is installed on trust in a URL. The catalog is signed with **Ed25519**; the webapp verifies it against a keyring committed in the base repository (a test fails if any other key appears), and each archive must match the SHA-256 the signed catalog gives it. The catalog's `serial` may never go backwards, so an attacker cannot replay an older catalog to hide a revocation. Only the official `redamon-plugins` catalog is trusted by default; another catalog's key is an explicit admin opt-in (`PLUGINS_EXTRA_TRUSTED_KEYS`) with a warning. An offline install must bring a catalog and signature that cover the archive and goes through exactly the same checks. An update that asks for more permissions than the admin granted waits for the admin to approve them again (`plugin.permissions_granted`). The runner image's own Python dependencies are pinned (`test_runner_requirements_pinned.py`).

**Third-party threat feeds are treated as untrusted input, not as data we trust.** The supply-chain incident catalog (supplychainattack.org) is fetched by a sidecar that is host-pinned (the allowlist is re-checked on every redirect hop), byte-capped, envelope-validated, and runs `cap_drop: ALL` with no Neo4j, Postgres or Docker-socket access. Its volume is mounted **read-only everywhere except that sidecar** and is deliberately absent from the broker's `ALLOWED_RW_VOLUMES`, so a compromised scanner cannot poison the intel other scans then trust. Because anyone can get an advisory published, every field is gated on the way in: hostnames against an LDH charset (prose entries and slash-joined garbage are dropped **and counted**), IPs against `is_global` so a poisoned entry cannot make RedAmon flag its own infrastructure, package names against the same `sanitize_name` used for subprocess arguments, incident URLs against an http(s) scheme check (they reach `<a href>` sinks, and React renders a `javascript:` href without complaint), and free text capped. A feed that returns no indicators at all is refused rather than allowed to overwrite good data with an empty set. The incident prose reaches the agent through `query_graph` wrapped in the same unforgeable `UNTRUSTED_GRAPH_DATA` boundary tool output gets, decided from the executed Cypher rather than the result text so a column alias cannot turn the containment off.

## 19. Verification and assurance

- **Each fix is independently verified.** Security remediations shipped in sequenced waves; each carried a unit/regression test and, where it was an exploitable weakness, a **before-and-after exploit reproduction** (for example SSRF, cross-tenant access, prompt injection, orchestrator auth, image injection, container escape).
- **Release gate.** A security remediation suite (`tests/run_security_remediation_suite.sh`) aggregates the suites and must pass before a security release, including live end-to-end probes (a single-user cross-tenant read attempt, the WebSocket ticket + origin gate, and the tunnel-auth gate). A separate two-user cross-tenant end-to-end test (`tests/test_e2e_bola_live.sh`, 40 checks) exercises the full impersonation chain.
- **Post-deploy asserts.** The deploy verifies the loopback network model, datastore binding, container health, admin presence, and the health endpoint on every run (see [Section 3](#3-network-exposure-and-the-single-public-origin)).
- **Coverage is broad.** Representative test files: `webapp/src/lib/access.test.ts`, `access.composition.test.ts`, `tests/test_e2e_bola_live.sh`, `agentic/tests/test_prompt_safety.py`, `test_ssrf_exploit_reproduction.py`, `mcp/servers/tests/test_auth_middleware.py`, `recon_orchestrator/tests/test_orchestrator_auth.py`, `tests/test_port_bindings.sh`, `docker_broker` policy tests.
- **Plugin isolation is probed from inside.** `tests/plugins_isolation_live.sh` (live, run against a stack started with `./redamon.sh up`; not part of the unit gate) runs a probe inside the runner under a worker-range UID and inside the proxy, and fails on any leak: the internet, Postgres, Neo4j, the agent, kali-sandbox, the orchestrator, the webapp other than through the proxy's two prefixes, the host through either plugin network's bridge address, a write to `/plugins`, or the environment of PID 1 or of a running worker. Around it: the runner's hostile-plugin and auth suites (`services/plugin_runner/tests/test_supervisor_hostile.py`, `test_supervisor_auth.py`, `test_gateway_proxy.py`), the compose wiring and the generated plugin secrets (`tests/redamon_plugins_profile_test.sh`, `redamon_plugins_env_test.sh`), the edge (`tests/deploy_plugins_nginx_test.sh`), and the webapp's call-token, catalog-signature and Gateway tests (`webapp/src/lib/plugins/callToken.test.ts`, `catalogVerify.test.ts`, `keyring.test.ts`).

## 20. Documented residual risks

Maturity means naming what is not yet closed. The following are accepted and tracked, not hidden:

- **Local-posture weaknesses are LAN-reachable.** In the default local posture `webapp:3000`, `agent:8090`, and `4444` publish on `0.0.0.0`; several app-layer conveniences (some agent REST routes that derive identity from the request body or are unauthenticated, the dev fail-open of certain service keys, no login lockout at the network edge) are only reachable from the LAN. The hardened deploy compensates with loopback binds, the session gate, the operator gate, and the secrets gate. Do not expose the raw stack on a public IP; use `tooling/deploy/single-host/`.
- **Plaintext secrets at rest.** Per-user LLM/OSINT keys are stored in the database without application-layer encryption, accepted for a single-operator, loopback-database host.
- **Body-derived tenant for master-key callers of the graph read proxy.** From the sandbox, `/graph/exec` and `/text-to-cypher` take the tenant from the run credential. The webapp, which holds the master key, still names the tenant in the body: it derives it from its own database, so a master-key holder can read any tenant's graph.
- **Service tokens stay readable inside the sandbox.** `MCP_AUTH_TOKEN` and `TUNNEL_AUTH_TOKEN` stay in the kali-sandbox servers' environment because they validate inbound calls to services in that container. No shell or tool child inherits them, but every server runs as root, so a root shell (`docker exec`, or the terminal) still reads them from `/proc/<pid>/environ` (measured in the RBAC experiment E3). With `MCP_AUTH_TOKEN` such a shell can call the Metasploit session manager (`:8013`) as the agent does (list, type into, kill or re-link any user's session) or drive `msfconsole` itself; the bearer keeps out the other containers on the Docker networks (the targets on `pentest-net` included) and host loopback, not the sandbox's own shells. The agent also receives `TUNNEL_AUTH_TOKEN` from `.env` without any `agentic/` code reading it.
- **Any user's shell or agent in the shared sandbox can read another user's live run credential.** The Kali sandbox is one container for every user, and every process in it runs as root. A `graph` credential sits in the environment of a terminal's shell and of every process started from it; a `traffic` credential and its `REDAMON_CTX` tag sit in the environment of one `proxy_brain` child. Another user's `kali_shell`, `execute_code` or terminal reads them from `/proc/<pid>/environ` (for example `grep -a REDAMON_RUN_CREDENTIAL /proc/*/environ`) and can present them. A graph credential opens `/graph/exec` (read-only queries of the victim's project graph) and `/text-to-cypher` (questions answered with the victim's model key, counted against the victim's rate limit and daily cap); a traffic credential with its tag opens `/traffic/exec`, `/traffic/replay` and `/traffic/browser` (the project's captured traffic, and replays and browser sessions against that project's targets through the capture proxy, in the run's phase). The window: a graph credential works until the terminal connection it was handed to closes (the tab closed, `/ws/close`, or 12 hours); a traffic credential for 15 minutes from the `proxy_brain` call that carried it, although the child holding it lives at most 180 seconds. A refused credential is logged (`[rbac] run credential refused reason=<code>`); a stolen one that is accepted is not told apart from its owner's. Closing this needs a sandbox, or at least a non-root uid, per user; until then the people who hold the terminal or whose agents may run `kali_shell` can reach every other user's open terminal and running `proxy_brain` call.
- **Tool secrets readable in the sandbox outside the servers' environment.** A user's chisel auth, WPScan token and URLScan key no longer travel on a command line or stay in a shared file: chisel gets its auth as `AUTH`, wpscan its token as `WPSCAN_API_TOKEN`, each only in its own child's environment, and gau reads the URLScan key from a per-call file (mode 600) removed when the call ends. What remains readable by a root process in the sandbox: the ngrok authtoken in `/root/.config/ngrok/ngrok.yml` while a tunnel is configured (passing it as `NGROK_AUTHTOKEN` instead would leave it as readable in the long-lived ngrok process's environment); the chisel auth in the chisel process's environment while the tunnel is up; a WPScan token, URLScan key or ProjectDiscovery key (`cve_intel`) in its child's environment or file while that call runs; and any key the agent or a person writes into a command's own arguments.
- **One user MCP toolset per agent process.** Runs of owners whose MCP Tool Plugin sets differ cannot run at the same time: the later one is refused with `mcp_toolset_busy` (a member with no servers included, so that no run reaches another owner's servers and their tokens) until the other ends. A per-run toolset is the closure.
- **Exfiltration to a public custom LLM endpoint.** A bring-your-own provider pointed at an attacker-controlled public endpoint is indistinguishable from a legitimate one; an opt-in operator allowlist is the planned closure.
- **Fail-open service keys in dev; internal-key allowlist log-only by default.** The webapp/agent internal-key check fails open with a warning when its secret is unset (the agent routes listed under Fail posture in [Section 8](#8-service-to-service-authentication) answer 503 instead), and the internal-key route allowlist is enforced only with `INTERNAL_KEY_ALLOWLIST_ENFORCE=true`; `redamon.sh` generates the secrets on install and the deploy secrets gate refuses to boot without them.
- **No CSRF token and no JWT revocation.** State-changing routes rely on `SameSite=Lax` cookies (no separate CSRF token), and login tokens are stateless for 7 days with no server-side denylist, so logout only clears the cookie and a stolen token cannot be revoked before expiry.
- **Weak password floor on self-service change.** The password-change route enforces only a minimal length; the first-admin bootstrap requires a stronger minimum. Operators should set strong passwords (the hardened posture's login rate-limit is the only brute-force brake).
- **DNS-rebinding TOCTOU on the SSRF guards.** Outside tradecraft and workspace URL imports, the guards resolve then hand off to an HTTP client that re-resolves at connect time. Tradecraft's HTTP fetches pin the address at connect time; its Playwright fallback resolves names inside Chromium, where neither rebinding nor the blind request a redirect hop sends is closed. Workspace URL imports pin every connection and never use a browser, so neither gap applies to them.
- **Target-facing containers run `seccomp`/`AppArmor` unconfined.** The Kali sandbox and the GVM scanner disable the default syscall filter (needed by some tooling); they are isolated on `pentest-net` and hold no master secret. The broker still forbids `unconfined` for the tool containers it spawns.
- **GVM ships with a default internal credential.** The optional GVM stack defaults to `admin/admin`; it is reachable only on the internal `pentest-net`, not from the edge, and is not part of the secrets gate.
- **Scanner spawns are not fully hardened.** Spawned scan containers get `NET_RAW`-only, the scoped scanner key and their scan's job credential (good for that one tenant and project until it expires) but are not `cap_drop`ped or `no-new-privileges`; they are constrained by the broker, the segment, and holding no master secret.
- **Plugins share one container.** Plugins are separated by process and UID inside one runner container, not by container; one container per plugin is the next step if stronger isolation is needed. Workers have no per-process CPU-rate limit (they run at `nice 10`; the container's `cpus` is the hard bound).
- **Plugins see target data.** A plugin granted `session:read` reads the session transcript, which carries tool output from live targets. Credential-shaped values are masked, but free text is not anonymised; containment relies on the trusted catalog and on the plugins network having no egress.
- **A frozen plugin catalog is not detected.** A rollback to an older catalog is refused, but an old, validly signed catalog served on by whoever controls the connection is not, because catalogs do not expire.
- **The reviewer is the control on plugin overrides.** An approved override can rewrite the agent's instructions, the scope text included; risk flags help, but a person who approves without reading defeats the control.
- **Agent in the Loop hands target text to a client RedAmon does not control.** A step's prompt carries tool output from live targets to the person's own agent, which may hold tools of its own on the person's machine. The skill pack tells the client to treat prompt text as data and its templates turn off the client's shell, web and file-write tools, but RedAmon cannot enforce what the client does with them; the person's client configuration is the control. The client also keeps its own transcripts (Claude Code for 30 days by default).
- **No CI-side security automation.** There is no CodeQL / Dependabot / secret-scanning / image-scanning workflow; the security remediation suite is a manual release gate and build sources are pinned by hand.

The authoritative, current status lives in the **[Changelog](../../CHANGELOG.md)** security entries and the **[Threat Model](README.TM.SYSTEM_OVERVIEW.md)**.
